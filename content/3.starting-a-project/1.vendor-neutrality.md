Vendor neutrality is a core principle and a primary objective of the Eclipse Foundation governance model.

Operating in a vendor-neutral manner is a goal for all Eclipse open source projects, and requires a clear separation between decisions made by participating companies and collaborative development in open source projects.

> **Tip:** Operating in a vendor-neutral manner requires effort. It may require a change in the way that your developers work. As such, it helps to regard moving your project to the Eclipse Foundation as a *process*, not an *event*. All Eclipse open source projects start in the [Incubation Phase](/incubation/).

When you move your project to the Eclipse Foundation, it becomes an *Eclipse* project. Specifically, it ceases to be *your* project and becomes a vendor-neutral *community* project that operates under the governance of the Eclipse Foundation.

This means, for example, that the open source project name and the names of any software produced by the project are trademarks (either registered or common-law) of the Eclipse Foundation, and you are required to follow the same [Eclipse Foundation Trademark Usage Policy](https://www.eclipse.org/legal/logo-guidelines). as everybody else when you refer to the project. If you were to, for example, contribute the "Woolsey" product to the Eclipse Foundation, you would be required to transfer all rights that you have to the name "Woolsey" to the Eclipse Foundation, and the use of the "Woolsey" name in your products, website, marketing materials, etc. would then be subject to the trademark policy (you would be required to rename your products from "Woolsey" to "\[Product Name\] for Eclipse Woolsey" or similar; there can be no notion of a "professional" version or similar of the Eclipse project). If the name is important to your organisation, consider choosing a different name for the Eclipse open source project.

The duration of the relationship between the project and the Eclipse Foundation is *forever*: when we create the project, it will be an Eclipse project that the Eclipse Foundation manages in a vendor-neutral manner on behalf of the community. If your team chooses to walk away from the project, the community will be able to pick up and continue the work.

Eclipse open source projects are required to operate in an [open, transparent, and meritocratic manner](/overview/#principles). This means that, as an Eclipse open source project, project developers ([committers](/project-roles/committers/)) are required to do their day-to-day work in the [Git repositories](/project-resources-and-services/gitlab-github-decision-matrix/) provided by the Eclipse Foundation (either [GitHub](/project-resources-and-services/github/) organisations and repositories managed by the Eclipse Foundation, or the Eclipse Foundation’s hosted [GitLab](/project-resources-and-services/gitlab/) instance). This includes issue trackers: the project team is required to track the addition of new features, and mitigation of bugs using [issue trackers](/project-resources-and-services/issue-trackers/) provided by the Eclipse Foundation (GitHub or GitLab Issues). The project team is expected to review merge/pull requests from the community, confirm that contributors are correctly covered by a valid [contributor agreement](/contributing/eclipse-contributor-agreement/), and merge contributions with technical merit that align with the project’s goals and scope. Further, the project team is expected to invite regular [contributors](/contributing/contributors/) to the project to join as committers.

Please see [Level Playing Field](https://blog.waynebeaton.ca/posts/opensource/level-playing-field/) and [Barriers for Entry](https://blog.waynebeaton.ca/posts/opensource/repository/).

The Eclipse Foundation Security Team will likely receive [vulnerability](/vulnerabilities/) reports for the project content. We regard this as a fundamentally good thing (vulnerability reports are an indicator that people care about the project). The security team will contact the project’s [security team](/vulnerabilities/project-security-team/) to disclose vulnerabilities, but these will be reported publicly after a period of time, whether they are addressed or not.

Project committers are required to engage in our [Intellectual Property Due Diligence Process](/intellectual-property/) to vet the licence compatibility of the third party content that the project leverages. Due diligence must be complete before any content is included in a [release](/releases-and-reviews/).

Eclipse open source projects operate entirely in the open. The Git repositories are entirely public. Every commit that project developers create must be immediately available to the community.

Please review the [Project Checklist](/project-checklist/).

It’s also important to know what new projects don’t give up. The project team retains control of the project’s direction by virtue of regular contribution to the project. The contributors to the project retain ownership of their contributions (those contributions are used under license by the project). Project leads are required to ensure that other individuals who present themselves to the project are given uniform opportunity to participate, but the project team gets to establish the rules for participation (within certain parameters). The project team is responsible for determining development methodology, establishing plans, etc. Existing owners of the project code retain their ownership.
